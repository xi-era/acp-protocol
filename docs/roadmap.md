# ACP 项目开发落地策略

> 背景:**已有 AI 编码工具,直接和大厂编码 Agent 硬刚没有胜算,转型做 ACP 分布式元件协议基础设施**
> 核心逻辑:不和大厂卷"对话/编码能力",大厂做上层应用,我们做下层协议标准;大厂要解决远程硬件、分布式组件,反而需要兼容我们的 ACP。

## 一、战略定位(先把思路对齐)

❌ 不要再做:更强的代码补全、更好的 Agent 对话、更聪明的编码工具(OpenAI、Cursor、字节、Claude 资金模型碾压,正面打不赢)
✅ 转型做:**Agent 分布式元件互联标准(ACP 协议)**

- 你的原有编码工具,变成 **ACP 的第一个官方客户端/参考实现**,而不是主打卖点
- 卖点:你的编码工具可以原生对接 ACP,调用全网远程硬件、微服务、IoT 元件;其他编码工具(Cursor/Aider)靠适配器接入 ACP
- 竞争格局:大厂可以做编码 Agent,但很难快速定义一套开源的、中立的、面向硬件/IoT 分布式的元件调用协议;协议标准一旦形成生态,就拿到差异化护城河。

> 一句话对外叙事:
> "我们曾经做 AI 编码工具,发现上层应用内卷严重。因此转向底层基础设施 ACP,解决所有 Agent 都要面对的远程、硬件、分布式组件调用问题。"

## 二、开发优先级排序(分 3 阶段,v0.1 → v0.2 → v1.0,最小可行优先)

### Phase 1:v0.1(MVP,1-2 个月,核心目标:协议跑通、可演示、Github 可开源)

**目标:不要做全量企业功能,先把协议本体、基础 SDK、最小适配器做出来,可以跑通 Demo。**

1. **定义 ACP 协议规范(文档优先)**
    - 元件元数据定义:`component_id`、输入输出 JSON Schema、描述、版本标签
    - 报文:发现元件、调用元件、流式分片返回、错误码体系;严格做极简 JSON,拒绝 JSON-RPC 冗余
    - 传输层:先实现 HTTP + WebSocket;Stdio 作为可选兼容(桥接 MCP 用)
    - 安全 metadata 预留字段(鉴权 token、权限域、traceId,v0.1 只做预留,不实现复杂鉴权)

    > 协议文档单独放仓库 `spec/ACP-0.1-SPEC.md`,这是整个项目最重要资产。

2. **最小 SDK 实现(选主力语言,建议 TypeScript/Node.js)**
    - `acp-sdk`:服务端(开发 ACP 元件)、客户端(调用 ACP 元件)两套基础 API
    - 只实现核心:注册元件、发现、调用、流式返回、错误处理。不要过早加网关、权限。

3. **acp-cli 命令行工具**
    - 本地调试:发现远程 ACP 元件、调用、查看报文,开发者调试必备。

4. **两个关键适配器(决定生态兼容性,最高优先级)**
    - ✅ ACP → OpenAI Tool-Call:把 ACP 元件自动转成大模型可以识别的工具定义,**你的原有编码工具直接接入这套适配器,立刻就能调用 ACP 元件**
    - ✅ ACP ↔ MCP 双向桥接适配器:
      - MCP 客户端可以调用 ACP 元件
      - ACP 客户端可以调用 MCP 本地工具

    > 这一步是破圈关键:不需要说服别人迁移,现有 MCP 生态直接复用。

5. **Demo 示例(必须写,开发者看懂怎么用)**
    - Demo 1:把一个简单 HTTP 后端 API 包装成 ACP 元件
    - Demo 2:模拟 IoT 硬件(虚拟传感器)作为 ACP 远程元件
    - Demo 3:你的旧编码工具,作为 ACP 客户端调用上面两个元件,录演示 GIF 放到 README

> v0.1 不做:网关、SSO、审计、企业权限;只做协议、SDK、CLI、适配器、Demo。
> 开源发布,面向个人开发者,拿到第一批早期使用者。

### Phase 2:v0.2(生态扩展,2-3 个月,构建开发者生态)

1. 多语言 SDK:至少 Python SDK(LangChain 生态刚需);Go SDK(硬件/边缘场景)
2. 完善元件规范:版本管理、元数据标签、心跳保活,适配嵌入式设备的轻量化模式(报文压缩选项)
3. 扩展适配器:LangChain 集成封装;简单示例:让 Cursor 通过 MCP-ACP 桥接调用远程 ACP 元件
4. 元件示例库:一批可直接复制的 ACP 元件模板:数据库、HTTP 代理、模拟 IoT
5. 你的原有编码工具迭代:**突出 ACP 原生支持作为差异化亮点**
    - 对外话术:市面上编码 Agent 大多只能跑本地工具,我们原生支持调用远程硬件、分布式业务组件。

> 此时开始社群运营:面向 IoT 开发者、工业 AI、企业内部 Agent 开发群体,而不是只卷普通程序员写代码。

### Phase 3:v1.0(商业化基础设施,面向企业客户)

1. **ACP-Gateway(商业闭源核心产品)**
    - 元件注册中心、权限管控、调用限流、审计日志、Trace 链路、SSO 登录
    - 管理大量 ACP 元件,统一鉴权,企业不会直接暴露 ACP 元件公网
2. 私有化部署包,企业交付方案
3. 高级桥接服务、元件市场(可选)
4. 商业收入:网关许可、私有化部署、咨询定制开发元件

## 三、原有编码工具如何定位?不要丢掉存量

1. **不要废弃原有编码工具,降级为 ACP 的官方参考客户端**
    - 产品介绍不再主打"最强编码 Agent"
    - 主打:**原生支持 ACP 协议的 AI 编码工具,一键调用远程业务、硬件元件;其他编码工具需要适配器桥接**
    - 原有用户继续维护,作为种子用户,用来打磨 ACP 真实场景。

> 对外叙事案例(README、社群、访谈):
> > "我们之前深耕 AI 编码工具,在产品迭代中意识到,上层 Agent 竞争已经非常白热化。但无论哪款 Agent,都很难优雅调用跨机器、硬件、IoT 分布式组件。因此我们沉淀出 ACP 协议,把之前编码工具中积累的 Agent 调用能力抽离出来,做成开放标准。我们自己的编码工具会原生支持 ACP,同时开放给 Cursor、Aider、LangChain 整个生态。"

这套叙事非常正向:不是做不下去编码,而是看到更大的底层机会,主动转型做基础设施。

## 四、避开大坑(非常关键)

1. ❌ 不要 v0.1 就堆企业功能,协议没有跑通,做网关权限都是空中楼阁。协议规范是第一位。
2. ❌ 不要和 MCP 做对抗。所有文档、对外发言反复强调:互补、桥接,不替代。MCP 有庞大生态,不要站在它对立面。
3. ❌ 不要只面向编码开发者,重点打 **IoT、边缘、工业自动化、企业内部 Agent 平台开发者**,这是大厂薄弱的蓝海。大厂 MCP 主打 PC 本地开发场景,远程硬件是缺口。
4. ❌ 不要闭门造车写协议。开源后积极收集反馈迭代 spec,邀请外部开发者贡献元件示例。

## 五、风险与护城河分析

- 风险:大厂后续也做类似协议。
- 护城河来源:
  1. **开源先行,抢先建立规范与开发者生态**,大量 IoT/边缘开发者基于 ACP 写元件;
  2. MCP 桥接层,兼容现有生态,迁移成本低;
  3. 聚焦硬件+分布式这个细分赛道,大厂的协议更多优先服务自家产品,而 ACP 是中立开源标准;
  4. 企业网关商业产品,协议开源,商业实现做壁垒。
